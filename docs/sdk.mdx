`@spyglass/sdk` is a ~5KB gzipped TypeScript SDK. rrweb (session replay) loads
lazily as a second chunk, only when `replay` is on, so apps that don't record pay
nothing for it.

The public surface is deliberately tiny — four methods:

```ts
import { spyglass } from "@spyglass/sdk";

spyglass.init(config);             // start everything
spyglass.capture(name, props?);    // a custom event
spyglass.setUser({ id, name?, email? }); // late / changed identity
spyglass.report(comment, extra?);  // programmatic bug report
```

---

## Installing

`@spyglass/sdk` is **not on npm** — GPL, self-hosted, and meant to work behind an
air gap. Pick one of these.

### Recommended: a private registry or a git dependency

If you can run [Verdaccio](https://verdaccio.org/) or install from a git URL, do
that. It behaves like any other dependency and sidesteps everything below.

### Otherwise: vendor it

From a spyglass checkout:

```bash
scripts/vendor.sh /path/to/your-app
```

That builds the SDK, checks it against its 5KB budget, packs it, and copies the
result to `your-app/vendor/spyglass-sdk` with a `VENDORED.json` recording the
source commit and whether the tree was dirty. Then:

```bash
pnpm add file:./vendor/spyglass-sdk
```

It copies rather than symlinks deliberately — see below.

### Hazards, all of them silent

These are the things that go wrong, and none produces a useful error.

<Callout type="warn">
  **`npm link` does not work in a pnpm project at all.**

```
npm error Cannot read properties of null (reading 'matches')
```

npm cannot parse pnpm's `node_modules` layout. There is no workaround; use the
vendor script.

</Callout>

**A cross-repo `link:` breaks under Turbopack.** pnpm accepts
`pnpm add link:../spyglass/sdk`, and then the bundler rejects it: Turbopack
resolves a symlinked dependency to its **real** path and refuses anything
outside the workspace root it infers from the lockfile. You get
`Module not found: Can't resolve '@spyglass/sdk'` while Node and `tsc` both
resolve it fine.

Pointing `turbopack.root` at the shared parent appears to fix it and is a trap.
Measured on a host app with ~11 sibling projects, each carrying its own
`node_modules`:

|                            | Default root | Root at shared parent |
| -------------------------- | ------------ | --------------------- |
| First `/dashboard` compile | 1.5s         | **over 2 minutes**    |
| An API route               | 62ms         | 51–93s                |

It also changes what `output: standalone` traces. Copy the package into your
repo instead, so the real path is back inside your workspace root — which is
what `scripts/vendor.sh` does.

**Only the core entry is safe to link.** Importing `@spyglass/sdk/next` from a
linked package loads a **second copy of React**, because the bundler resolves
`react` through the symlink into the SDK's own `node_modules`. The resulting
hook errors point nowhere near the cause.

The core entry imports nothing external, and `npm run size-check` in `sdk/`
asserts that on every build:

```bash
$ cd sdk && node size-check.mjs
core: 4.34KB gz (budget 5KB)
core entry has no external imports -- safe to link
```

**The package is ESM-only.** There is no `require` condition and no CJS build —
a dual-package hazard is worse than this papercut. A CJS tool that needs to
locate the package should resolve its manifest, which is exported for exactly
this reason:

```js
const { createRequire } = require("node:module");
const req = createRequire(__filename);
const pkgDir = require("node:path").dirname(req.resolve("@spyglass/sdk/package.json"));
```

`require.resolve("@spyglass/sdk")` itself still throws `ERR_PACKAGE_PATH_NOT_EXPORTED`,
by design.

## `init(config)`

Call once, as early as possible. Throws if `endpoint`, `app`, `key`, or
`user.id` is missing.

```ts
spyglass.init({
  endpoint: "https://telemetry.internal.acme.dev",
  app: "inventory",
  key: "sg_live_…",
  user: {
    id: "anand",
    name: "Anand",
    email: "anand@acme.dev",
    traits: { role: "Partner", team: "audit" },
  },
  replay: true,
  context: true,
  network: true,
  maskInputs: "password",
  reportWidget: true,
});
```

### Config options

| Option          | Type                             | Default            | Notes                                                                                  |
| --------------- | -------------------------------- | ------------------ | -------------------------------------------------------------------------------------- |
| `endpoint`      | `string`                         | —                  | **Required.** Collector base URL.                                                      |
| `app`           | `string`                         | —                  | **Required.** App slug; must match a key in the collector config.                      |
| `key`           | `string`                         | —                  | **Required.** App key for ingest auth; must match `apps.<slug>.key`.                   |
| `user`          | `{ id, name?, email?, traits? }` | —                  | **Required** (`user.id`). All sessions are identified. See [Traits](#user-traits).     |
| `replay`        | `boolean`                        | `true`             | rrweb session replay + console capture.                                                |
| `context`       | `boolean`                        | `true`             | Coarse session context (viewport, screen, UA, language, timezone, referrer).           |
| `network`       | `boolean \| { bodies }`          | `true`             | Capture fetch/XHR metadata. See [Network capture](#network-capture).                   |
| `maskInputs`    | `"all" \| "password" \| "none"`  | `"password"`       | Input masking in replays.                                                              |
| `reportWidget`  | `boolean`                        | `true`             | Floating bug-report button.                                                            |
| `flowTimeoutMs` | `number`                         | `1800000` (30 min) | A flow open longer than this is forgotten, not slow — see [Flow timing](#flow-timing). |
| `minAbandonMs`  | `number`                         | `100`              | Abandonments faster than this are remounts, not decisions. `0` records every one.      |

## `capture(name, props?)`

Record a custom event. `props` is any JSON-serializable object.

```ts
spyglass.capture("invoice_created", { amount: 1200, currency: "USD" });
spyglass.capture("filter_applied"); // props optional
```

Event names are the building blocks of [funnels and aggregates](/docs/dashboard#insights),
so keep them stable and snake_case.

---

## `setUser({ id, name?, email? })`

Update the identified user after `init()` — e.g. once a login resolves, or when
a user switches accounts. Fields you pass are merged into the current user.

```ts
spyglass.setUser({ id: "anand", name: "Anand Lahoti" });
```

---

## `report(comment, extra?)`

Emit a `bug_report` event programmatically — the same event the floating widget
produces. Useful for a custom "Report a problem" entry point.

```ts
spyglass.report("totals look wrong on the invoice screen", { severity: "high" });
```

Every bug report becomes an [incident](/docs/dashboard#incident-view): the replay
slice around the moment it was filed, cued and ready to watch.

## Flow timing

`capture` answers _how often_. A flow answers _how long_: the span between a
user committing to an action and finishing, or giving up on, it.

```ts
spyglass.startFlow("task.create", { entry: "keyboard" }); // the form opened
spyglass.endFlow("task.create", { clients: 3 }); // the task exists
```

`endFlow` returns the elapsed milliseconds (or `null` if the flow was never
started, or had timed out) and emits a single `flow` event carrying
`duration_ms`, an `outcome`, and the start and end props merged. Query it with
[`GET /v1/query/flows`](/api#get-v1queryflows).

| Call                                | Outcome     | Use for                                                             |
| ----------------------------------- | ----------- | ------------------------------------------------------------------- |
| `endFlow(name, props?)`             | `completed` | It worked.                                                          |
| `cancelFlow(name, reason?, props?)` | `abandoned` | The user gave up — dialog dismissed, navigated away mid-form.       |
| `failFlow(name, reason?, props?)`   | `failed`    | It broke. A failed save, a server rejection — not the user's doing. |

Keeping the last two apart is what stops "slow because it is confusing" and
"slow because it errored" averaging into one uninformative number.

```ts
// Handle form, for when start and end sit in the same scope:
const f = spyglass.flow("invoice.create");
f.end({ items: 3 }); // or f.cancel("dismissed") / f.fail("server_error")

spyglass.isFlowActive("task.create"); // → boolean
spyglass.activeFlows(); // → string[]
```

### What the design decides for you

- **`startFlow` on an open flow restarts its clock.** A user who reopens the
  form is starting over; the abandoned first attempt should not be charged to
  the second.
- **Ending a flow that is not open is a no-op.** That is what makes the common
  pattern work with no coordination: end the flow on success, cancel it when the
  dialog closes, and the cancel that follows a successful save emits nothing.
- **A flow open longer than `flowTimeoutMs` is dropped, not reported.** Someone
  left the form open over lunch. Reporting a four-hour "task creation" would
  poison every percentile it lands in.
- **An abandonment faster than `minAbandonMs` is ignored.** React StrictMode
  runs effects mount → cleanup → mount in development, so the natural pattern —
  start on mount, cancel on cleanup — would emit a 0ms abandonment on every page
  visit and peg that flow's abandon rate near 50%. Completions are never
  filtered: an action that genuinely finishes in 40ms is a real measurement.

### Flows across pages

Open flows live in `sessionStorage`, so a flow survives navigation within the
tab and dies with it — a wizard spanning three pages is still one flow.

`startFlow` also works before `init()`, because it only writes to storage. That
is how you time a login: start the flow on the login page, where there is no
user to attribute it to, and close it from inside your auth gate once spyglass
has been initialised. The event is attributed to the user who arrived.

```tsx
// login page
useEffect(() => {
  spyglass.startFlow("auth.login");
}, []);

// inside the authenticated layout, right after spyglass.init(...)
spyglass.endFlow("auth.login");
```

## What gets recorded automatically

With the defaults, `init()` alone wires up the following. None of it needs extra
code.

### Pageviews

Captured automatically in Next.js via [`<SpyglassProvider>`](#nextjs). In plain
apps, call `spyglass.capture` on route changes, or send a pageview yourself.

### Session replay

rrweb records the DOM continuously and uploads gzipped ~10-second chunks. Console
logs travel **inside** the replay stream (via the official console-record
plugin), so the replay player shows a synced console pane — no separate pipeline.

Backpressure rule: if uploads can't keep up, replay is dropped **before** events.
Analytics integrity is never sacrificed for replay.

### Network capture

Patches `fetch` and `XMLHttpRequest`. By default records **metadata only**:
method, URL, status, duration, and request/response sizes.

Request/response **bodies are opt-in per route prefix**:

```ts
spyglass.init({
  // …
  network: { bodies: ["/api/orders", "/api/invoices"] },
});
```

Only URLs matching an allowed prefix have their body captured, truncated to 2KB.
`Authorization` and `Cookie` headers are **never** recorded. The collector's own
requests are never intercepted. Set `network: false` to disable entirely.

### Error tracking

Hooks `window.onerror`, `unhandledrejection`, and patches `console.error`.
Captures the message, source, line/column, and stack. Identical errors within a
5-second window are de-duplicated so a render loop doesn't flood the feed.

### The bug-report widget

A floating 🐛 button (bottom-right) opens a comment box with an optional severity.
Submitting emits a `bug_report`. It renders inside a **closed Shadow DOM**, so
your app's styles and the widget's never bleed into each other. Turn it off with
`reportWidget: false` and use [`report()`](#reportcomment-extra) instead.

## Next.js

`@spyglass/sdk/next` exports a provider that starts everything `init()` does —
error tracking, network timing, replay, the report widget — and wires app-router
pageviews through `usePathname` / `useSearchParams`:

```tsx title="app/layout.tsx"
import { SpyglassProvider } from "@spyglass/sdk/next";

<SpyglassProvider config={{ endpoint, app, key, user }}>{children}</SpyglassProvider>;
```

The provider takes the exact same config object as `init()`.

**Mount it inside your auth gate, not at the root.** `config.user.id` is
required and a provider above the login screen has no user to name; mounting it
below the gate also stops you recording the one screen where a password is
typed, which beats masking it.

If you are linking the SDK from a sibling checkout rather than installing it,
import only `@spyglass/sdk` and write your own ~30-line provider. The `/next`
entry imports `react`, which a bundler resolves through the symlink to the SDK's
own copy — two Reacts, and hooks stop working. The core entry has no external
imports at all.

## How delivery works

You don't manage any of this — it's documented so you know the guarantees.

- **Batching.** Events queue in memory and flush every 5 seconds or every 20
  events, whichever comes first.
- **Never lose tab-close events.** On `visibilitychange` / `pagehide` the queue
  is flushed with `navigator.sendBeacon`, which survives the page going away.
- **Sessions.** A random session ID lives in `sessionStorage`; a new one is
  minted after 30 minutes of inactivity.

## User traits

`user.traits` carries queryable **cohort** attributes, so a question can be
asked about a kind of user rather than one person:

```ts
spyglass.init({
  user: { id: "PARV0004", traits: { role: "Partner", team: "audit", admin: false } },
});

spyglass.setUser({ id: "PARV0004", traits: { role: "Manager" } }); // traits update too
```

Query them with `group=trait:<key>` or narrow with `trait=<key>:<value>` on
[`/v1/query/flows`](/docs/api#get-v1queryflows):

```
/v1/query/flows?name=task.file&group=trait:role
/v1/query/flows?name=task.file&trait=role:Employee
```

This is the difference between "PARV0004 is slow at this" — an awkward thing to
put in front of a manager — and "Employees are slower at this than Partners, so
the form assumes knowledge they don't have", which is a finding about the
software. `group=user` gives one row per person: readable for 40 people, noise
for 200.

**Traits are recorded per session**, alongside the session context, so they are
historically honest: a task filed while someone was an Employee stays attributed
that way, and promoting them does not rewrite the past.

**Scalars only.** Strings, numbers, booleans and `null` are kept; objects,
arrays and functions are dropped rather than serialised. At most 24 traits, keys
up to 40 characters, string values truncated at 120.

<Callout type="warn">
  Traits describe a **cohort**, never a person. Role, team, plan, tenure bucket — not email, not
  phone, not a client name. The SDK enforces the shape, not the judgement.
</Callout>
