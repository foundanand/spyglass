The dashboard is a single embedded page served at the collector root
([http://localhost:7474](http://localhost:7474) by default). No separate process,
no Node on the server — it ships inside the binary. If a
[dashboard password](/docs/configuration#auth) is set, the browser prompts for it
once.

## How it is organised

Five sections, named after the question each answers rather than after how the
data is stored:

| Section       | Answers                         |
| ------------- | ------------------------------- |
| **Home**      | Is everything OK?               |
| **Behaviour** | What are people doing?          |
| **Sessions**  | Who did it?                     |
| **Issues**    | What broke?                     |
| **Boards**    | The numbers you check regularly |
| **Explore**   | The raw event stream            |

A **time range picker** sits in the nav and applies to every view — 24h, 7d, 30d,
90d, All, defaulting to **30 days**. It lives in the URL (`#/behaviour?range=7d`),
so any view you are looking at can be pasted to a colleague.

### One rule worth knowing

> Every aggregate leads to the rows behind it. Every row leads to a session.
> Every session leads to a replay.

That is at most three clicks from any number to watching a person hit the
problem. It works because spyglass records **every** session continuously with
identified users — so unlike a sampling tool, every number really does have a
watchable recording behind it.

## Home

The landing page, and the only one that is not a table. Each tile and list is a
_finding_, and each links to the thing that explains it:

- **Active users, errors, bug reports** — each with the change against the
  previous equal-length period.
- **Flows that got slower** — p90 this window against p90 last window. Nothing
  else in the tool surfaces a regression, and it is the most useful thing a home
  page can say.
- **New error types** — signatures that were not happening before. Far more
  actionable than a total.
- **Recent bug reports** — a human took the trouble to file these.
- **Most abandoned flows**, and a short strip of the latest _deliberate_ actions.

When nothing needs attention, it says so rather than making you infer it.

## Behaviour

The analyses: daily active users, errors by day, top events, top pages, the
**flow duration table**, and the **funnel builder**.

Every row here is a link. A day in a chart opens that day; a top page opens its
screen page; a top event opens Explore filtered to it; a flow name opens its
flow page.

### Flow page

Reachable by clicking any flow name. It answers the four questions a duration
immediately raises:

- **Median, p90, abandon rate, total time spent**, with the change against the
  previous period.
- **A distribution histogram.** A median and a p90 hide a split — "half finish
  in 2s and half take two minutes" looks the same as a steady spread in
  percentiles.
- **A breakdown** by person, day, device size or role.
- **The slowest sessions**, listed, each one click from its recording. This is
  the point of the page.

### Screen page

Reachable from top pages. Views, distinct visitors, **what broke on this
screen** — previously unanswerable without reading URLs by hand — and the recent
sessions that visited.

## Sessions

The user list, and each user's sessions with chronological breadcrumbs.

### User page

Reachable from any user id anywhere in the product. Their sessions, their errors
and reports, and **their flow timings against the overall median**.

That last table is framed deliberately: a gap is a question about the software —
whether a flow assumes knowledge or a screen size this person does not have —
not a judgement about the person. "Employees are slower at this than Partners"
is a product finding; "PARV0004 is slow" is a performance review, and this tool
should not be used to write one.

## Issues

Errors and bug reports, filterable by type and user, newest first. Every row
opens the incident view. Pages backwards through history, and exports to CSV
with the filters you are looking at.

## Boards

Every question you asked spyglass used to be thrown away when the tab closed.
The flow table and funnel builder both take real input, and neither could be
named, saved, or put beside another one — so the tool answered questions but
never accumulated.

Configure the flow table or funnel on **Behaviour** and press **save this
view**. A board is a named, ordered set of saved views on one page: "the four
numbers we check every Monday", and something you can hand a colleague rather
than instructions for recreating it.

This is persistence and layout, not a query language — a saved view stores the
parameters a panel is already using, so a board can never ask something the
dashboard could not.

A board inherits the dashboard's time range rather than pinning its own, so its
panels stay comparable. Views are global: the collector has one shared password
and no user model. Deleting a view removes that panel from any board using it;
the board keeps working.

## Explore

The raw event stream — the escape hatch, not the front door.

It defaults to **activity**: everything except network requests. On real data
network events are around 89% of a session (one measured 25-minute session
logged 254 of them against 17 pageviews, 9 errors and 4 captures), which buried
everything worth reading. Network is one chip away, every chip carries a count,
and the feed states plainly what it is hiding.

Paging backwards pauses the live poll so the ground does not move while you
read, and says so.

## Incident view

The reason spyglass exists. For **any** error or bug report, it assembles the
slice from `[ts − 60s, ts + 10s]` of that same session and lays it all out on one
page:

- **The replay clip**, auto-cued to the exact moment it happened.
- **A breadcrumb timeline** — every event in the window.
- **A network waterfall** — the requests around the failure, with status and
  duration.
- **The console output** from the replay stream.
- **The stack trace** (errors) or **the comment and severity** (bug reports), on
  top.

This is the Capture.dev / Jam product — "show me exactly what happened when it
broke" — except nothing was specially captured. Because the system records every
session of every identified user continuously, the incident is just a **query**
over data already on disk. You open it after the fact; there was no ring buffer
to have been running, no repro to reproduce.

Reach it by clicking any row in **Issues** or **Explore**, from a new-error or
bug-report tile on **Home**, or by hitting
[`GET /v1/incidents/:event_id`](/docs/api) directly.

Clicking a breadcrumb, or a row in the network waterfall, seeks the player to
that moment — the difference between reading an incident and watching it. Those
rows are real controls, so a keyboard reaches them too.
